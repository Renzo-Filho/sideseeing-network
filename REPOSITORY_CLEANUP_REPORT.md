# Repository cleanup and architecture report

**Audit date:** 17 September 2026  
**Status:** approved and executed. The `export/` folder was explicitly preserved in place and was not modified.

## Executive conclusion

The repository is visually messy, but most of its disk use is legitimate research state rather than disposable duplication.

- `analysis/` is the canonical project workspace and should remain so for the current research cycle.
- The 15 GB in `analysis/data/` and 3.4 GB in `analysis/work/` are tied to source manifests, accepted evidence, frozen preparations, or resumable runs. They should not be deleted.
- The clearest removable clutter is at the repository root: the old `notebooks/`, root `cache/`, root `data/` link tree, empty scaffold folders, generated bytecode, and a fully duplicated `export/` tree.
- Safe generated/cache cleanup would recover about **149 MB**. Removing the duplicate export and superseded notebooks as well would recover about **183 MB**. The repository will remain large because the large files are mainly required source and lineage data.
- The current `analysis/results/`, `analysis/work/`, compatibility-link, and release layout is already well designed. The largest structural improvement is to separate current documentation from historical plans/audits and eliminate the parallel root-level prototype workspace.

## Evidence reviewed

This audit read `README.md`, `plan.md`, all Markdown documentation under `analysis/`, the result and work-area READMEs/reports, `.gitignore`, `pyproject.toml`, the tracked-file inventory, current Git status, folder sizes, symlinks, code/path references, notebook markers, and exact-file hashes.

Important findings:

- There are no broken local Markdown links in the current documentation.
- `analysis/outputs` and `analysis/processed` are compatibility symlinks, not duplicate physical datasets.
- The frozen SP v2 and v3 preparations are both consumed by the accepted attribute release. The documentation explicitly says both are required.
- The working tree contains current, uncommitted Chicago work. Cleanup must not overwrite or fold those changes into an unrelated operation.
- `export/` contains 146 files: 105 exact copies of files already under `analysis/`, 40 generated `.pyc` files, and one export-specific README. Its 44 dataset files are byte-for-byte identical to `analysis/results/SP/`.
- The root `notebooks/analysis.*` and `notebooks/chicago_bras_analysis.ipynb` use simulated/random accessibility values. They conflict with the current research protocol, which requires accepted measurements and prohibits premature Chicago–Brás ranking.
- The three numbered root notebooks are older exploratory analyses. They are not linked from the current documentation, but they contain unique historical exploration and should be approved separately from the simulated prototypes.

## Documentation issues to fix during reorganization

The documents are detailed and generally consistent, but their location and status labels can be clearer.

1. `analysis/notes/README.md` still says that no similarity model has been fitted, although SP model v2 is complete. The release-specific attribute report may correctly say it produced no model, but navigation pages should state the current project stage.
2. `plan.md` links to the compatibility path `analysis/outputs/.../REPORT.md`; it should link to the canonical `analysis/results/SP/reports/ATTRIBUTE_REPORT.md`.
3. `analysis/notes/SP_ATTRIBUTE_IMPLEMENTATION_PLAN.md` mixes an old planned state with later completion notices. Preserve it as historical design material, but move it under an archive/status-qualified location.
4. `analysis/SP_MODEL_VALIDATION.md` is a resolved historical failed audit. It should remain available but be moved under an archive/audits section so readers do not mistake it for current status.
5. `pyproject.toml` describes a generic sidewalk-extraction package, Python `>=3.9`, and six dependencies, while the documented project uses Python 3.12 and a much larger analytical stack from `analysis/requirements.txt`. It should become the single environment/package declaration or clearly defer to a lock/requirements file.
6. The authoritative navigation should identify exactly one current status document per city and mark method specifications, historical audits, and release reports by role.

## Proposed folder structure

The safest target keeps large artifacts in their current paths while separating current documentation, executable code, notebooks, and historical records.

```text
sideseeing-network/
├── README.md                       # concise project entry point
├── plan.md                         # current research protocol
├── pyproject.toml                  # accurate Python/tooling definition
├── REPOSITORY_CLEANUP_REPORT.md
├── docs/
│   ├── README.md                   # documentation map and status legend
│   ├── sp/
│   │   ├── attributes.md
│   │   ├── methods.md
│   │   ├── model-v2.md
│   │   └── building-pipeline.md
│   ├── chicago/
│   │   ├── attributes-v1.md
│   │   ├── functional-v2.md
│   │   ├── data-requirements.md
│   │   └── harmonization-plan.md
│   ├── operations/
│   │   └── handoff.md
│   └── archive/
│       ├── plans/
│       └── audits/
└── analysis/
    ├── README.md                   # workspace/data navigation only
    ├── config/                     # versioned executable contracts
    ├── scripts/                    # current CLI entry points and modules
    ├── tests/                      # current automated tests
    ├── model_analysis.ipynb        # current validated SP notebook
    ├── model_analysis.py           # checked notebook export
    ├── data/                       # ignored canonical raw inputs
    │   ├── SP/
    │   └── Chicago/
    ├── cache/                      # reproducible acquisition caches
    ├── results/                    # compact published releases
    │   ├── SP/
    │   ├── Chicago/
    │   └── SP_CHI/                 # future accepted comparison only
    ├── work/
    │   ├── prepared/
    │   ├── evidence/
    │   ├── runs/
    │   └── reviews/
    └── .compat/                    # documented legacy path adapters
```

### Why this structure

- The root contains only project-wide entry points.
- `docs/` separates current SP methods, current Chicago work, operations, and historical material.
- `analysis/` has one job: executable analysis plus local/published artifacts.
- Only validated, current notebooks remain visible.
- Results remain beside their release READMEs and validation evidence rather than being copied into documentation.
- Large frozen paths do not move, avoiding invalidated manifests and multi-gigabyte churn.
